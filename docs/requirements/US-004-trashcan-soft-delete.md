# User Stories: Art Reference Archive — Trash, Restore, and Permanent Deletion

## US-004 — Move pictures to trash, restore them, and permanently delete them

**Story:** As the archive owner, I want deleting a picture to move it to a trash area that I can restore it from or permanently delete it from, so that a mistaken delete costs me nothing but a click to undo — my image and its tags come back exactly as they were — while I can still remove a picture for good when I really mean it.

**Acceptance Criteria**

1. Given the archive contains 5 active pictures and the trash is empty, when the user deletes one of those pictures and confirms, then the gallery lists exactly 4 active pictures, the deleted picture is not among them, the trash view lists exactly 1 picture — that same picture — and the application therefore still retains all 5 pictures (4 active and 1 trashed), while the other 4 pictures keep the same tags and the same viewable images as before the delete.
2. Given a picture tagged "nature" and "tree" has just been moved to the trash, when the user views the gallery with no tag filter, views the gallery filtered by "nature", asks the random viewer for a picture filtered by "nature", and runs the slideshow filtered by "nature", then that picture is never listed or displayed in any of those four cases, and every other active picture carrying "nature" is still eligible.
3. Given the only picture tagged "sky" has been moved to the trash, when the user asks the random viewer for a picture filtered by "sky" or runs a slideshow filtered by "sky", then the application states that no pictures match the filter and never returns the trashed picture in its place.
4. Given a picture with the tags "nature" and "tree" and a viewable image has been moved to the trash, when the user opens the trash view, then that trash entry displays the same image at a viewable size and shows the tags "nature" and "tree" unchanged from before the delete.
5. Given a picture was moved to the trash, when the application is restarted and the gallery and trash views are opened, then the picture is still listed in the trash with its image and its tags unchanged, it appears in no active view, and no other picture's tags or image have changed.
6. Given a picture with the tags "nature" and "tree" is in the trash, when the user restores it and the restore completes, then the picture appears again in the active gallery exactly once with the tags "nature" and "tree" unchanged, it no longer appears in the trash, and it is returned by the gallery filter "nature", by the random viewer filtered by "nature", and by the slideshow filtered by "nature".
7. Given a picture was restored from the trash, when the application is restarted, then the picture is still an active picture with its tags unchanged and it is not listed in the trash.
8. Given a picture is in the trash, when the user permanently deletes it and confirms, then the picture is removed from the trash, its stored image file is no longer present in the application's picture storage, no view lists it, and no action available in the application can bring it back.
9. Given a picture is in the trash, when the user starts a permanent deletion, then a confirmation is displayed that identifies the picture and states that it will be removed permanently and that this cannot be undone, and nothing about the picture changes until the user confirms.
10. Given a picture is in the trash, when the user starts a permanent deletion and then cancels or dismisses the confirmation, then the picture remains in the trash with its tags and image unchanged, it is still restorable, and its stored image file is still present.
11. Given at least one picture is in the trash and at least one picture is active, when the user opens the trash view, then only trashed pictures are listed and no active picture appears; when the user opens the gallery with any tag filter, the random viewer, or the slideshow, then no trashed picture appears in any of them.
12. Given a picture is already in the trash, when a delete is requested for that picture again — for example from a browser tab that still shows it as active — then the request is rejected with a message stating the picture is already in the trash, the trash still lists exactly one copy of that picture, the active and trashed picture counts are unchanged, no second copy of the image is created, and the picture's tags are unchanged.
13. Given a picture is active and not in the trash, when a restore is requested for it, then the request is rejected with a message stating the picture is not in the trash, the picture remains active exactly once with its tags unchanged, and the contents of the trash are unchanged.
14. Given a trashed picture whose stored image file is missing, when the user opens the trash view, then the application does not crash, the trash view still opens and lists the remaining trashed pictures, that entry is marked as having an unavailable image, and no other picture's tags or image change; when the user attempts to restore that entry, then the restore is refused with a message stating the image is unavailable, the picture stays in the trash, and the stored data of every other picture is unchanged.
15. Given a trashed picture whose stored image file is missing, when the user permanently deletes it and confirms, then the picture is removed from the trash without an error, the trash view still loads afterwards, and no other picture's tags or image have changed.
16. Given a picture was permanently deleted from another view or another browser tab, when the user attempts to restore or permanently delete it from a trash view that still lists it, then the request is rejected with a message stating the picture no longer exists, no picture is created or re-added, no other picture's data changes, and the trash view refreshes to show only the pictures actually in the trash.
17. Given the archive has 3 active pictures, 2 pictures in the trash, and 1 picture that was previously permanently deleted, when the application is restarted and the gallery and trash views are opened, then the gallery lists exactly the 3 active pictures, the trash lists exactly the same 2 pictures as before the restart, and the permanently deleted picture appears in neither view and its image cannot be retrieved.
18. Given 6 active pictures with distinct tag sets and viewable images, when the user moves one picture to the trash and permanently deletes another from the trash, then the remaining 4 pictures keep exactly the same tags as before and their stored images are unchanged, still viewable, and still returned by the same tag filters as before.
19. Given the tag "sky" is carried only by a picture that has been permanently deleted, when the user filters the gallery, the random viewer, or the slideshow by "sky", then no picture is returned and the application states that no pictures match the filter; given the tag "nature" was carried by both the permanently deleted picture and a picture that remains active, then the remaining picture is still returned for "nature".
20. Given a picture is currently displayed in the random viewer or the slideshow, when the user moves that picture to the trash from that view and confirms, then that view stops displaying it immediately and never displays it again, and every other picture the view shows behaves as before.

**Priority:** Must-have (MoSCoW)

**Related requirements:** No `REQ-###` or `UC-###` is assigned to this capability yet; this story is the origin of the IDs for the trash view, restore, and permanent-deletion capability. Related stories: US-002, "tag editing and deletion," covers adding and removing *tags* on a picture and does not remove pictures; the picture-deletion behavior its title suggests is specified here, and this story follows it by relying on the existing single-picture selection and gallery behavior it defines. This story does not depend on US-003: it requires no global tag rename or global tag delete, and every criterion above holds whether or not US-003 is implemented. US-001 is related in that pictures imported from a ZIP archive can be moved to the trash, restored, and permanently deleted like any other picture, with no special handling.

**Assumptions / dependencies:**

- Terminology used in this story: a *soft delete* (the user-facing "delete") removes a picture from every active view while keeping its stored data and its image file; a *permanent delete* removes both the stored data and the image file.
- Depends on the existing single-image upload, ZIP import, gallery with AND-semantics tag filtering, random viewer, and slideshow continuing to behave as they do today except for the exclusion rules in AC 2, AC 3, AC 11, and AC 19; no filtering semantics change is requested.
- Depends on `data.json` plus the `uploads/` folder remaining the only persistence for pictures — no new service, database, or second storage location is introduced — and on the design data-model invariants I4 ("no picture without a stored image file") and I5 ("the stored archive is replaced whole, so no partial state is observable") continuing to hold through every trash, restore, and permanent-delete action.
- Confirmed scope: the soft delete replaces permanent deletion as the default meaning of the existing delete control everywhere it appears (gallery, random viewer, slideshow); restoring and permanently deleting an individual trashed picture are the only two actions offered on a trashed picture.
- Confirmed scope: emptying the trash in a single action is out of scope for this story. Each trashed picture is restored or permanently deleted on its own. If bulk emptying is ever added it must be a separate story with its own confirmation behavior.
- Confirmed scope: there is no second-level trash and no undo of a permanent deletion; the confirmation in AC 9 is the only safeguard.
- **Not prescribed here — design decision:** how trashed state is represented is left to the design artifact. Whether it is an indicator carried on each picture's stored data, a separate grouping of pictures, or another arrangement, this story fixes only the observable behaviors above. A direct consequence the design must satisfy: any picture whose stored form carries no trash indicator must be treated as active, so the 7 existing records load as active with no migration, no rewrite on read, and no new required data.
- Depends on a trashed picture keeping its tags unchanged while it is in the trash: tags are neither deleted, renamed, nor edited as a side effect of a soft delete, and they are restored exactly as they were (AC 4, AC 6, AC 12).
- *Assumption to validate:* trashed pictures are excluded from any "how many pictures use this tag" count shown before a global tag rename or tag delete (the count US-003 describes), because those counts describe active pictures. Confirm with the requirements owner whether a US-003 global rename or delete should also reach pictures sitting in the trash; AC 2 and AC 11 require only that trashed pictures stay out of active views and results.
- *Assumption to validate:* restoring a picture whose stored image file is missing is refused rather than returning a broken picture to the gallery (AC 14), because an active picture with no image is exactly the dangling state the design data model forbids. Confirm this is the intended behavior rather than "restore anyway and show a placeholder."
- *Assumption to validate:* the display position of a restored picture is not prescribed by this story. It must appear exactly once and be visible in the gallery; whether it returns to its previous position or to the end of the order is a design choice.
- Confirmed scope: no automatic expiry. Pictures stay in the trash indefinitely until the user restores or permanently deletes them; no time-based purge, storage quota, or retention window is introduced.
- The application is single-user and unauthenticated, so every trash, restore, and permanent-delete action is available to whoever is using the application; no ownership, role, or permission rules apply, and no concurrent-editor conflicts are possible beyond the stale-view cases in AC 12 and AC 16.
- Confirmed scope: a message accompanies every rejected or refused action in AC 12–AC 16, so a stale view never fails silently.
- **Edge cases considered:** deleting the last picture that matches a filter, leaving nothing for the random viewer or slideshow to return (AC 3); deleting the picture currently on display in the random viewer or slideshow (AC 20); a repeated or double-clicked soft delete, or a delete from a stale tab (AC 12); a restore requested for a picture that is not in the trash (AC 13); a trashed picture whose image file has gone missing — the trash view must still open, the entry must be identifiable, and restore must be refused while permanent delete still works (AC 14, AC 15); a picture permanently deleted in another tab and acted on from a stale trash view (AC 16); a restart with a mixed active/trash state and an already permanently deleted picture (AC 5, AC 7, AC 17); permanently deleting the only picture that carried a tag, so that tag matches nothing, versus a shared tag that must still return the surviving picture (AC 19); a soft delete or permanent delete that must not alter any other picture's tags or image file (AC 1, AC 5, AC 15, AC 18); a trashed picture must be retained as a picture — not merely remembered as a filename — so that its image and tags are intact on restore (AC 4, AC 6, AC 7); cancelling the permanent-delete confirmation at the last moment (AC 10); a failure part-way through any trash action must not leave a picture both active and trashed at once, duplicated, or missing (AC 12, AC 16, AC 18).
